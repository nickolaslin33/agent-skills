# reentry — 重新進入工作狀態

給人看的安裝與使用說明。Agent 執行時讀的是 [`SKILL.md`](SKILL.md)。

## 這個 skill 解決什麼問題

你請 AI agent 做了一整天的事，隔天或隔一個週末再回來接手。這時候通常會發現：不只忘了做到哪裡，連當初為什麼那樣決定、還有哪些沒確認的部分，都一起變模糊了。

更麻煩的是另一種情況：agent 交付的內容你當時只看了個大概就繼續往下推進。後續工作因此建立在不完整的理解上，等到真的需要修改時，補回這些理解的成本會比當初直接搞懂高得多。這類尚未補足的理解，這個 skill 稱為**理解債**。

所以它做兩件事：

- **收工時**引導你留下一份完整到足以重建當時工作狀況的紀錄，並用一個獨立的 agent 檢查你的描述與實際產出是否一致。
- **回來時**把那份紀錄照固定順序讀出來，順序與用詞都不改寫。

## 安裝

```bash
npx skills add nickolaslin33/agent-skills@reentry
```

腳本只用 Python 3 標準函式庫，不需要另外安裝套件。

## 第一次設定

### 1. 建立資料目錄

```bash
mkdir -p ~/reentry
```

預設路徑是 `~/reentry`。想放別的位置就設環境變數，例如寫進 `~/.zshrc`：

```bash
export REENTRY_ROOT="$HOME/work/reentry"
```

### 2. 替要追蹤的專案建立資料夾

```bash
mkdir -p ~/reentry/orders-api
```

**只有建了資料夾的專案才會被納入管理**。這是刻意的設計：建資料夾等於你主動宣告「這個專案我還在做」。沒有資料夾的專案不會出現在清單裡，agent 也不會自動幫你補建。

想讓某個專案退出，直接刪掉它的資料夾。

### 3. 建議把資料目錄納入版本控制

```bash
cd ~/reentry && git init
```

有兩個原因。第一，理解債的每個項目都會記下對應的 `commit SHA`，之後要回答那個問題時得靠 git 歷史找回當時的 diff。第二，`artifacts.md` 與 `handoff.md` 每次收工都會覆寫，沒有版本控制的話，前幾次的紀錄就找不回來了。

這個目錄會包含你各個專案的工作內容摘要，**如果推到遠端，記得設為私有**。

## 怎麼開始互動

不需要記特定指令，用平常講話的方式就會觸發。

### 回來的時候

```
我回來了
繼續 orders-api，上次做到哪了？
我忘記做到哪了
我有哪些東西還沒做完？
```

沒有指定專案的話，agent 會先列出所有已登記的專案讓你挑；指定了就直接讀那一個。

輸出順序固定：警告（如果上次的理解落差很大）、上次叫它做什麼與做到哪裡、上次的決定（如果有）、還沒補的理解債、下一步。**下一步放在最後是刻意的**——先看完前面的內容，比較不會在還沒掌握前因後果的情況下就直接動手。

### 收工的時候

```
今天到這了，幫我記一下進度
收工
先記一下進度
```

接下來會有四個階段，總共大約 2 到 3 分鐘：

1. **agent 會請你關掉工作畫面，憑記憶寫四項**：你原本叫它做什麼、做到哪裡；下一步；三到五個關鍵詞；還不確定的地方。這一步要在看不到 diff 的情況下完成——看著答案評估自己懂不懂，測不出實際的理解程度。
2. **agent 檢查你寫的內容**，最多回報三項落差。它判斷的不是「你寫的對不對」，而是「這句話單獨拿給一個沒參與的人看，指不指得出對象」——它有這次的對話紀錄，所以標準得外部化，不然會自動幫你補完。事實不符的部分會直接指出；理解層面的判斷只會標成「agent 認為」，你可以反駁。
3. **你根據檢查結果修正**。原始版本會保留，你寫的與修正後的差異就是這次的理解債。
4. **agent 整理任務狀態，並把該追蹤的理解錯誤記進 `debt.md`**。判斷標準很窄：只有「為什麼必須這樣設計」這類講錯了才算；記錯檔名、行數、測試數量不算，那屬於記憶誤差。

第三階段留下的理解債不會另外安排時間處理，而是整合在下一次收工的檢查裡：每次挑一項舊問題請你回答，答對就標記完成。


### 一個完整的例子

第一次用會不知道該寫多細。下面是一整個 session 從頭到尾長什麼樣。

**情境**

`orders-api` 最近常因為下游服務短暫不通而失敗，錯誤直接回給使用者。你接到的任務是
讓它遇到這種狀況時自己重試。你不打算自己寫，而是逐步讓 agent 處理。

**你陸續給 agent 的指令**

1. 「把 `place_order()` 的 retry 抽出來，我不想每個 handler 都寫一遍」
2. 「retry 要能設定次數跟間隔」
3. 「跑一下測試」
4. 「間隔改成每次加倍」
5. 「這樣下游一直不通會等到多久？加個上限」

**agent 實際做的**

- 新增 `src/orders_api/retry_utils.py`
- `handlers/orders.py`、`handlers/refunds.py` 改用它
- 新增 `tests/test_retry_utils.py`，8 個測試
- 第二輪把固定間隔改成每次加倍，並加了上限 `max_backoff`

**收工時你寫的四項**

```markdown
## 我叫它做什麼，做到哪裡
叫它把 retry 從各個 handler 抽成共用模組。中間改過兩次——先做成可設定次數與
間隔，後來改成每次間隔加倍並加了上限。兩個 handler 都換過去了，測試 8 個過。

## 下一步
跑 retry 測試

## 關鍵詞
retry-utils, 間隔加倍, max_backoff, handler 共用

## 不確定的地方
不確定上限設多少合理，現在是隨手填的 30 秒
```

第一項寫的是**你要它做什麼、以及它交出了什麼**，不是逐條複述那五個指令。中間改過
方向這件事有寫進去，因為那是隔一段時間之後最難自己想起來的部分。

### 要寫多細

看你想對這個專案理解到多深。不同專案的答案不一樣，同一個人也不需要全部統一：

| 你需要知道的 | 紀錄寫到 |
|---|---|
| 今天在做什麼事就好，不需要知道用了哪些工具 | 一句話交代任務與進度 |
| 某支程式在做什麼，但不需要知道它內部怎麼寫 | 模組名稱、它負責什麼、改動的方向 |
| 要能直接接手繼續改 | 加上關鍵函式、參數、還沒處理的狀況 |

上面那個例子落在第二層。

**下一步這一項有兩種寫法，都可用：**

有餘裕的時候寫成這樣，回來可以直接動手：

```
把 refunds 的 retry 上限調成跟 orders 不同（退款可以等更久），
改完跑 tests/test_retry_utils.py
```

趕時間的時候至少寫到這樣，回來知道從哪裡切入：

```
跑 retry 測試
```

第一種比較好，因為回來時不用再想一次要做什麼。但寫不出第一種不代表要留空白——
第二種仍然給了起點，而空白等於下次回來要從零開始判斷。

**這只是範例，不是規定**。如果你對今天做的事很有想法，寫多一點不是壞事，紀錄詳細
本身沒有壞處。要避免的是兩件事：拖太久，以及卡在回想上出不來。

## 不透過 agent，直接看

三支腳本都能在終端機單獨執行，適合只想快速看一眼的時候。

```bash
# 列出所有已登記的專案
python3 ~/.claude/skills/reentry/scripts/reentry_index.py

# 讀單一專案
python3 ~/.claude/skills/reentry/scripts/reentry_read.py orders-api
```

路徑依你的安裝位置調整。`$SKILL_DIR` 在 SKILL.md 裡指的就是這個目錄。

輸出範例：

```
orders-api  2 天前

上次叫它做什麼、做到哪裡
  叫它把第一階段的骨架跟 core 原語做完（clock / ids / config）。做完了。

上次的決定
  分層檢查規則寫進 setup.cfg，不放 pyproject.toml。

欠債 2
  - 為什麼分層檢查要帶 allow_indirect_imports = True？
  - 為什麼 domain 層連 store 都不能 import？

下一步
  第二階段（三個設定載入點：settings / tuning / limits），先做 settings

先用自己的話說一次下一步再動手。
```

## 資料長什麼樣

每個專案一個資料夾，底下四種檔案：

```
~/reentry/orders-api/
├── handoff.md      # 你憑記憶寫的四項，每次收工覆寫
├── artifacts.md    # 這次改了什麼、驗證結果，每次收工覆寫
├── debt.md         # 還沒補的理解債，持續累積
└── decisions/      # 決策紀錄，一個決定一個檔案
```

哪些可以手動改：

| 檔案 | 可以手改嗎 |
|---|---|
| `debt.md` | 可以。想標記某項已經理解，把 `- [ ]` 改成 `- [x]` |
| `decisions/` | 可以。也可以自己補寫決策 |
| `handoff.md` | 不建議。下次收工會整份覆寫 |
| `artifacts.md` | 不要。內容由腳本與 agent 產生 |

完整的格式規範在 [`references/file-formats.md`](references/file-formats.md)。

## 想知道每條規則的依據

[`references/evidence.md`](references/evidence.md) 列出每項設計的研究依據與證據強度，也誠實標出哪些部分目前沒有實證支持。想修改設計之前建議先看那一份——有些規則看起來可以簡化，但簡化之後就失去原本的作用。

## 檔案結構

| 路徑 | 用途 |
|---|---|
| `SKILL.md` | Agent 執行時讀的指引 |

| `assets/templates/` | 空白檔案模板 |
| `tests/` | 腳本的單元測試 |
