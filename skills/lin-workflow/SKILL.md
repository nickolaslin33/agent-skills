# LIN 工作流

## 這個 skill 要解決的問題

使用者把開發任務交給 agent 之後，審核時最花時間的是四件事：

- 要自己逐項追查 agent 說「已驗證」的證據。
- 修好 A，卻連帶改壞沒人注意的 B。
- agent 順手重構或擴大範圍，diff 變大，真正的修改被淹沒。
- agent 找到相似的舊程式就照抄，把不該再用的寫法帶進新程式。

這套流程的目的，是讓使用者只看「需要人判斷」的地方，其餘由 agent 提出可以查證的證據。所以流程裡的每一步都在回答同一個問題：使用者憑什麼可以不看這一段。

## 生效範圍

使用者指名之後，這個對話裡交代的開發任務都照這套流程做，直到使用者說不用。

流程要依任務大小縮放。改一行設定的任務，完工卡可以只有一段；涉及金額或共用模組的任務，每一步都要做完整。單純問答與讀程式碼不需要完工卡。

## 流程總覽

下表的編號對應後面各節的編號。

| 節 | 做什麼 | 產出 |
|---|---|---|
| 1．接任務 | 理解需求、查資料、必要時提問 | 任務卡 |
| 2．記錄起點 | 第一次寫檔之前執行腳本 | 每個相關 repo 一個 `start` 檢查點 |
| 3．實作與驗證 | 修改，驗 A 與 B | 修改、前後值、測試原始輸出 |
| 4．做到一半遇到要確認的事 | 發生在第 3 節進行中：先記下來，繼續做 | 待確認清單、檢查點 |
| 5．產生差異與獨立核對 | 執行腳本，另開唯讀 agent | 完整 diff、核對出來的問題 |
| 6．交完工卡 | 在原對話回覆 | 完工卡 |
| 7．使用者決定之後 | 刪除檢查點，或還原重做 | 乾淨的 repo 狀態 |
| 8．領域設定 | 接任務時查找，全程參照 | 這個專案特有的規則 |

腳本位置是 `"$SKILL_DIR"/scripts/lin_task.sh`（`$SKILL_DIR` 指本 skill 的安裝目錄，依實際安裝位置代入）。

## 1．接任務：先理解，再查資料，最後才問

需求不明確時不要立刻反問使用者。照這個順序處理：

1. **先寫出自己的理解。** 包含目的、範圍、要改對的結果 A、最容易被連帶改壞的行為 B，以及哪些地方不確定。
2. **查資料。** 讀相關程式碼、既有測試、規格、工單，以及同類功能的既有做法。能從資料確定的事不要問。
3. **仍然不確定才用問答釐清。** 一次問一題，從最會改變結果的問題開始。每一題附上已經查到什麼、有哪些選項、建議選哪一個。
4. **剩下的不確定處不會改變結果時，停止提問。** 自行選定，並寫在任務卡上。

A 與 B 的選法：

- **A** 用使用者、營運人員或下游服務看得到的行為描述，不要用「修改某函式」這種實作描述。
- **B** 從實際的呼叫端找：這次要改的函式、狀態或輸出格式還有誰在用。共用程式至少列出一個其他的使用方。

把任務卡貼給使用者之後直接繼續做，不用等回覆。使用者看到 B 選錯會主動說。

同時找出這個 repo 的**領域設定**，做法見第 8 節。

## 2．記錄起點

同一個工作目錄可能同時有使用者的草稿、已暫存的修改，以及你即將新增的內容。完工時要能回答「這一件任務到底改了什麼」，所以在第一次寫檔之前執行：

```bash
bash "$SKILL_DIR"/scripts/lin_task.sh start csv-discount "修正匯出 CSV 的折扣後金額"
```

- 任務代號（上例的 `csv-discount`）自己取，用英數字與連字號。
- 任務涉及多個 repo 時，每個 repo 各執行一次，使用同一個任務代號。
- 腳本不會改動工作目錄、暫存區與目前分支。檢查點存在 `refs/ai-task/` 底下，不會出現在分支清單，也不會被 push 出去。
- 腳本回報「未追蹤檔案過大」時，照訊息處理後再執行，不要直接略過檢查。
- 腳本因為環境限制無法寫入 `.git` 時，告訴使用者並請他核准。沒有起點就無法區分任務前後的修改，完工卡必須標明「歸屬待確認」。

## 3．實作與驗證

實作時的範圍規則：

- 每一組修改都要能對應到需求、必要的修正，或測試。
- 新的抽象、重排、整檔改格式、擴大 API，如果說不出這次任務為什麼需要，就不要做，改成另外的提議寫在完工卡最後。
- 必要的修改超出原本範圍時，在完工卡保留原範圍、超出的原因與影響。
- 找到相似的既有程式想照著寫之前，先對照領域設定裡的認可範例與已知舊寫法。

A 的驗法依任務類型而定：

| 任務類型 | A 怎麼驗 |
|---|---|
| 修 bug | 同一個案例在起點版本失敗、在修正後通過。 |
| 新功能 | 規格的正例與反例。 |
| 純重構 | 寫清楚允許的結構變動，同一組輸入的行為、資料與錯誤處理前後相同。 |
| 效能優化 | 同一負載下，事先約定的指標達到約定的數值。 |

B 分兩層驗證，能做第一層就做第一層：

1. **整包輸出比對。** 專案能固定輸入重播時使用。把起點匯出成舊版，拿同一批輸入分別跑舊版與新版，比對完整輸出，完工卡只列出有變動的欄位。這一層能發現事先沒想到的 B。

   ```bash
   bash "$SKILL_DIR"/scripts/lin_task.sh export csv-discount start /tmp/csv-discount-before
   ```

2. **指定 B。** 專案有保存的狀態或外部服務、無法整包重播時使用。固定輸入與設定，比對第 1 步選定的 B。這一層只能發現事先列出來的 B，完工卡要說明用的是這一層。

驗證時必須遵守：

- **先確認同一個版本重跑兩次的結果相同，再比新舊版。** 結果不同代表還有沒固定住的亂數或時間來源，這時的新舊差異不能當成程式行為變更的證據。
- **保留原始輸出。** 包含執行的命令、退出碼、實際執行的案例數與受測版本。你的解釋另外寫。對不到原始輸出的結論標「待驗」。
- **改到預期值要特別標示。** 如果同時改了實作與測試的預期答案、容許誤差或檢查規則，這件事放在完工卡「你需要看哪裡」的第一項，並說明新的預期值依據什麼規格或算例。
- **固定輸入的重播只能發現可重現的行為差異。** 隨機規則的驗收要用獨立樣本與事先約定的判定方式，做法見領域設定。

## 4．做到一半遇到要確認的事

不要停下來等使用者回答。照這個順序處理：

1. **記進待確認清單。** 寫明問題、為什麼會影響結果、哪些工作依賴這個答案。
2. **先做完不依賴這個答案的工作。**
3. **再處理依賴它的工作**，分兩種情況：

| 情況 | 判斷依據 | 做法 |
|---|---|---|
| 可以先用預設 | 有合理的預設，而且依賴它的修改只發生在 repo 的檔案裡。 | 記檢查點，用預設做完，再記一個檢查點。 |
| 不能用預設 | 找不到合理的預設，或預設錯了無法靠還原檔案補救。例如會寫入資料庫或測試環境、會 push、會部署、會送出訊息。 | 其餘工作做完後停在這裡，帶著問題問使用者。 |

第 2 步一定要排在記檢查點之前。兩個檢查點之間只包含依賴這個預設的修改，之後才能只還原這一段，不影響其他已完成的工作。

```bash
bash "$SKILL_DIR"/scripts/lin_task.sh ckpt csv-discount q1-before "Q1 折扣為 0 時欄位留空或寫 0？預設寫 0"
# 用預設完成依賴 Q1 的修改
bash "$SKILL_DIR"/scripts/lin_task.sh ckpt csv-discount q1-after "Q1 依預設完成"
```

檢查點的說明文字要寫出問題與採用的預設。對話內容被壓縮之後，`list` 指令的輸出就是待確認清單的備份。

預設涉及第 6 節「需要你判斷」的類別時仍然可以先做完，但這件任務不能列為可快審，而且這個決定要放在完工卡「你需要看哪裡」的第一項。

## 5．產生差異與獨立核對

完工前用腳本取得任務期間的完整差異，不要憑記憶列出改了哪些檔案：

```bash
mkdir -p /tmp/lin-task/csv-discount
bash "$SKILL_DIR"/scripts/lin_task.sh diff csv-discount -- --stat
bash "$SKILL_DIR"/scripts/lin_task.sh diff csv-discount > /tmp/lin-task/csv-discount/task.patch
```

把完整 diff 與測試原始輸出存到 repo 以外的資料夾。執行環境有提供暫存目錄時用它，沒有時用 `${TMPDIR:-/tmp}/lin-task/<任務代號>/`。

接著做獨立核對。每件任務都做第一項，涉及「需要你判斷」類別的任務四項都做：

1. diff 裡有沒有完工卡沒提到的修改。
2. 測試的預期值、容許誤差、檢查規則有沒有被改。
3. 有沒有遺漏的使用方。
4. 有沒有無法對應需求的改動，或沿用了已知的舊寫法。

做法：

- **執行環境可以開子 agent 時**，開一個唯讀的子 agent，把 `references/reviewer-prompt.md` 的內容原樣交給它，只附上任務描述、diff 檔、測試原始輸出與領域設定。不要附上你的推論或完工卡草稿，否則它容易直接接受你的說法。
- **不能開子 agent 時**，自己做第一項：從腳本的 `--stat` 輸出逐一核對每個改動的檔案是否都寫進完工卡。完工卡要標明「未做獨立核對」。
- **涉及「需要你判斷」類別時**，在完工卡建議使用者另開一個對話、最好換另一個模型，把審查提示詞與 diff 檔的位置交給它。

核對出來的問題先自己處理。處理後仍未解決的，寫進完工卡的「你需要看哪裡」。

## 6．交完工卡

在使用者交代任務的對話裡回覆。格式與完整範例見 `references/completion-card.md`。五個部分：

| 部分 | 寫到什麼程度 |
|---|---|
| 改了什麼、為什麼 | 一兩句，描述使用者看得到的行為在修正前後的差別。相同目的的多個檔案放在一起，附完整改檔清單。 |
| 你需要看哪裡 | 每項給一個判斷題、具體後果，以及可以點到那段程式的位置。沒有時寫「沒有待決事項」。 |
| 我自行決定了什麼 | 每項寫明問題、採用的預設與理由、哪些修改依賴它、檢查點名稱。沒有時省略。 |
| 已經驗過什麼 | A 與 B 的前後值、測試環境、原始輸出的位置，以及沒有驗的範圍。 |
| 哪些可以略讀 | 例如建立測試資料的程式、機械式搬移。附略讀的理由與完整 diff 的位置。 |

第一行標明交付狀態：

| 狀態 | 條件 |
|---|---|
| 可快審 | 需求明確、每段修改都能歸到任務、A 與 B 都有證據、獨立核對沒有未解決的項目，而且修改與自行決定的事項都沒有碰到下一列的類別。 |
| 需要你判斷 | 涉及金額與結算、保存的狀態、機率或設定表、共用模組或共用 API、對外封包或協定、架構，或兩份規格互相衝突。領域設定可以增加項目。 |
| 我先補 | 可重跑的測試沒跑或失敗、結果屬於舊版本、有修改沒交代、A 有測而 B 沒有證據。這種狀態不要交卡，補齊再交。只有需要使用者提供規格或取捨時，才帶著具體問題回來。 |

寫完工卡時必須遵守：

- **風險寫成「什麼條件會讓誰出錯，會看到什麼結果」。** 不要寫「可能有風險」「建議留意」。
- **證據完整度與出錯代價分開寫。** 測試全數通過不代表規則符合使用者的意思。
- **未驗的範圍如果可能影響這次決定，放進「你需要看哪裡」**，不要放在「可以略讀」。
- **不要把還沒做的事寫成已完成。** 測試沒跑就寫沒跑，並說明原因。

## 7．使用者決定之後

| 使用者的決定 | 做法 |
|---|---|
| 接受，自行決定的事項也都正確 | `clean` 刪除這件任務的檢查點。使用者要求提交時，commit message 帶完工卡的前兩部分。沒有要求就不要提交。 |
| 某個自行決定的事項方向錯了 | `undo` 還原那一段，依使用者的答案重做，重新驗證後再交卡。 |
| 整個方向錯了 | `rollback` 退回 `start`。 |
| 要求補證據 | 補齊後更新完工卡。之前的測試結果如果對應舊的檔案狀態，要重跑。 |

```bash
bash "$SKILL_DIR"/scripts/lin_task.sh list csv-discount
bash "$SKILL_DIR"/scripts/lin_task.sh undo csv-discount q1-before q1-after
bash "$SKILL_DIR"/scripts/lin_task.sh rollback csv-discount
bash "$SKILL_DIR"/scripts/lin_task.sh clean csv-discount
```

還原時要知道的事：

- **`undo` 與 `rollback` 會改動工作目錄，只在使用者確認方向錯誤之後執行。** 腳本執行前會自動多記一個檢查點，還原錯了可以再退回去。
- **`undo` 回報無法直接還原時，檔案不會被改動。** 原因通常是後來的修改動到同一段程式。參考腳本存下來的差異檔手動還原，並在完工卡說明。
- **多個預設互相依賴時**，還原前面的決定，後面依賴它的修改也要一起還原。
- **檢查點只能還原 repo 裡未被忽略的檔案。** 資料庫、測試環境、已 push 的 commit、外部服務的狀態都不在範圍內。submodule 與巢狀 repo 裡的修改，要進到該 repo 各自記檢查點。

## 8．領域設定

這套流程本身不限定專案類型。每個專案要另外提供四項內容，稱為領域設定：

1. 哪些改動一定要人判斷。
2. 改了什麼要附什麼證據。
3. 怎麼做可重現的新舊比對，例如要固定哪些亂數來源。
4. 認可的範例與已知的舊寫法。

接任務時依序尋找：使用者指定的檔案；repo 的 `AGENTS.md` 或 `CLAUDE.md` 裡標題含「領域設定」的段落或它指向的檔案。格式見 `references/domain-profile.md`。

找不到時使用本文件的通用規則，並在任務卡寫明「這個 repo 沒有領域設定，使用通用規則」。任務中發現應該寫進領域設定的事（例如找到一個之前沒固定住的亂數來源），在完工卡最後提出，由使用者決定要不要寫進去。不要自行修改領域設定。
